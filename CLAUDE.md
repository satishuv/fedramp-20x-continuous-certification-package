Guidance for Claude Code sessions working in this repository.

What this repository is: a generic, reusable framework for producing FedRAMP 20x Security Decision Records (SDRs). Everything derives from the canonical FedRAMP Consolidated Rules for 2026 (CR26) dataset pinned in references/. Read README.md first. If the local-only steering/ directory is present (it is excluded from the published repository), also read steering/source-register.txt and steering/session-state.txt for the current state of work.

Hard rules, no exceptions:

1. No fabrication. Missing facts are labeled TBD, Needs validation, Not applicable with justification, Planned, Gap, Exception, or FedRAMP pending. Never mark anything Implemented without real evidence.
2. No customer data, credentials, account numbers, internal endpoints, or restricted report content in any artifact. Synthetic examples only, always labeled as examples.
3. Every FedRAMP or Amazon Web Services (AWS) fact is checked against the sources in steering/source-register.txt, never asserted from memory. At session start, hash-compare references/fedramp-consolidated-rules.json and the pinned schemas in artifacts/schemas/official/ against the live copies; FedRAMP updates schema files in place without renaming them. github.com/FedRAMP/rules is the controlling upstream and a SessionStart hook reads it every session, including FedRAMP's own AGENTS.md (mirrored at ../hooks/fedramp-upstream/AGENTS.md), the dataset's JSON schema, and the published rules page. Read that report before changing requirement-bearing code or answering a requirements question, and repeat what it says if a source changed or the check did not complete. Never write a rule identifier without confirming it resolves in the dataset: rules nest as FRR -> process -> data -> applicability -> subset -> ID with applicability all, 20x or rev5, so reading only data['all'] hides every CSX rule and makes real identifiers look fabricated.
4. The human-editable content files are sdr/records/records-store.json (security-decision facts) and profiles/common/offering-profile.json (offering metadata and class). Never hand-edit generated outputs (traceability/, the rest of profiles/, sdr/json/, sdr/human-readable/, validation/reports/). Change the pipeline or the inputs, then regenerate.
5. Human-readable deliverables are clean plain text: numbered headings, consistent labels, no markdown symbols inside deliverable content.
6. JSON deliverables must validate against the official FedRAMP SDR schema with 0 errors. Provider extras live only in the isolated providerExtensions object and the extensions companion file.
7. All validation must pass (0 hard failures) before any commit. `python sdr.py all` runs the whole pipeline (catalogs, notes, profiles, SDR, Word, crosswalk, CPO/OCR/SCG, events, assurance graph, manifest, SBOM, validators, scanner) in the right order; call the individual validation/scripts/build_*.py only when debugging one stage. A change to the rendered SDR shape must be built for every class (`SDR_BUILD_CLASS=a`, `=c`, then the active class last) because all three classes' artifacts are committed and CI regenerates and diffs each.
8. Do not cite archived pilot material (RFC-0006 era KSI counts, RFC-0024, pre-CR26 workbooks with numeric KSI identifiers such as KSI-IAM-01) as current requirements.

Pipeline and class selection: set certification_class in profiles/common/offering-profile.json (A, B, or C), then run build_sdr.py, build_docx.py, and validate_sdr.py. Scripts resolve all paths relative to their own location; do not reintroduce absolute paths.

Two verification tools, different jobs. validate_sdr.py is the build gate: aggregate checks, one exit code, must report 0 hard failures before anything ships. automation/sdrscan/sdrscan.py is the assessment-readiness scanner: 38 checks producing one finding per rule and per indicator, each citing the CR26 rules that make it a requirement. It satisfies CDS-CSO-CBF (automation keeps the human-readable and JSON formats consistent) and FRC-CSX-VVR (automated methods persistently verify and validate the record). It reports and does not gate, because the template legitimately has open gaps; thousands of failures against the template is the correct result, not a regression. It never writes to the record store and never moves a status. Its check registry is mirrored in automation/sdrscan/check-catalog.json, which CI refuses if stale, so regenerate it with sdrscan.py --write-catalog after changing checks.py. Scanner reports under validation/reports/sdrscan/ are git-excluded build outputs. See automation/sdrscan/README.md.

Verified anchor numbers (recheck against the dataset if it changes; dataset 2026.10.13.01): 233 rules extracted of 245 entries; 46 KSIs in 10 families; provider profiles resolve to 41 rules and 7 KSIs at Class A (enumerated by FRC-CLA-MFR, not blanket), 157 rules and 46 KSIs at Class B and Class C (158 before FRC-CSX-MOT was removed in 2026.10.08.01); 156 rules in the Class D readiness register; every KSI in the dataset carries a statement (the earlier release in which 5 were empty is superseded); FRC-CSX-VVK test minimums are A 0, B 1, C 2, D 4.

Assurance beyond the validator: `audit/release_gate.py` is the single release-ready definition (sections audit, attack, attack-non-aws, security), run by GitHub Actions, the CodeBuild release path and `python sdr.py release`. When you fix a defect, add a mutation to `audit/mutation_tests.py` and a record to `audit/defect-ledger.json`; the runner fails on a surviving or skipped mutation and on a ledger that does not reconcile. A dependency change edits an input file and then `make lock` (or `make lock-security` for the scanners) regenerates the hash-locked lock and the SBOM. Documentation facts that CI tests: the dataset version in every pin claim and the derived counts sentence in README.md (`validation/scripts/test_docs_facts.py`), the class table (`test_docs_class_table.py`), and the living-loop privilege split (`automation/pipeline/test_living_sdr_privileges.py`).
